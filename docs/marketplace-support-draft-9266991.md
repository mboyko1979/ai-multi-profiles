# Draft — not sent

Reply to support request [9266991](https://marketplace-support.jetbrains.com/hc/en-us/requests/9266991).

Subject: AI Multi Profiles 35238 / beta 0.2.2 / update 1197250 — remaining Internal API integrations and request for supported extension points

Hello JetBrains Marketplace team,

Thank you for reviewing AI Multi Profiles. We investigated verifier results 6007581 (IU-262.10968.63) and 6007582 (IU-263.7031.23). Both contain 382 active Internal API findings and two ignored findings, covering 185 distinct active API elements. Most Air findings are generated pass-through methods from native interface delegation, rather than separate feature implementations. We understand that binary compatibility and absence of a public replacement do not authorize use of private APIs.

We prepared development 0.2.3-dev.2 using public `PluginDetailsService.isDisabled()` for disabled-state queries, the public Assistant ACP identity type's loader, and the documented dependency classloader graph with public `PluginAwareClassLoader.pluginId` for native module resolution. This removes plugin-descriptor/internal plugin-set lookup and reflective module enumeration, including the discovery initialization path. Public `UpdateSession.children()` also replaces the previous reflective override-only action-group expansion and restores native Air model/settings controls. The development artifact has not been uploaded to Marketplace.

The plugin resolves project profiles to an installed agent/account environment, then delegates the composer, model/settings controls, agent-owned catalog caches, preparation, tools, prompt admission, cancellation and completion to the native host. Choosing a launch profile is local to that composer and requires no live agent session. Profiles do not change the project Default Profile. Existing conversations restore their committed agent/profile segment; changing agent identity requires explicit consent before recovery/history transfer. We cannot remove these behaviors or replace native controls/lifecycle solely to avoid verifier findings.

Development 0.2.3-dev.2 passes `check buildPlugin`, the combined native Assistant/Air regression suite and Plugin Verifier 1.410 against both exact IDE builds with compatible host dependencies. Each complete unsuppressed report contains 373 Internal API findings across 183 distinct elements: eleven removed and zero added relative to uploaded 0.2.2, including its ignored entries. The public metadata service is Experimental on 262 (19 total experimental findings) and no longer Experimental on 263 (8). The native checks use controlled agents; full EAP native UI/production-provider coverage is not claimed. This version is for local verification only. The exact remaining API inventory and candidate-replacement assessment accompany this draft.

Could you direct us to supported APIs or confirm the exact permitted scope, versions and conditions for these remaining integrations?

1. Air composer-scoped launch decoration: `ThreadGuiPreparedSessionLeaseService[Impl].open`, `BackendThreadGuiPreparedSessionApi`, `PreparedSessionLease`, `ThreadGuiPreparedSessionRequest`, `AgentSessionRuntimeAdapters.resolvedOrNull`, and `ThreadGuiApi`/`ThreadGuiRef` delegation. We need to carry resolved profile launch arguments while Air retains native preparation/admission and cleanup. We do not want to replace application-wide launch factories or implement another preparation state machine.
2. Air agent identity/catalog mapping: `AcpAgentsCatalog`, `AcpCatalogEntry` (including `resolveStartConfig`), `AcpAgentId`, `AcpAgentStartConfig.withAcpArgs`, `acpCatalogAgentId` and `acpAgentLaunchTargetId`. We need the real bound agent's cache/catalog and folded Codex identity while routing the process through AI Multi.
3. Air presentation: `AgentDescriptor`/`AgentDeclaration` delegation, `AcpAgentCatalogContributor`, `AgentLaunchTargetPresentationServiceImpl`, `RowPresentation`, `AirPromptSelectorId.actionId` and `CompactAwareActionButtonWithText`. We need a narrow native composer profile contribution and profile/icon attribution for existing session identities, preserving unrelated agents and native controls.
4. AI Assistant UI/authentication: `AIAssistantChatPanelComponentProvider`, `AIAssistantChatPanelComponent`, `AgentAuthorizationRowProvider`, `AcpEvent.CustomAgentEvent` and `AcpUserResponse.RequestResponse`; native input/status contracts `AIInput`, `AgentSession` and `AIAssistantChatCustomNotificationViewModel`. These support setup, real authentication responses, unsent-draft protection and retained read-only history.
5. AI Assistant attribution and toolbar decoration: `SplitComponentProvider`, `SplitComponentBinding`, RPC `Id`, `ChatSessionId.findValue`, and `ExtensionPointImpl.maskAll`. We need a scoped native toolbar decorator and response-header contribution, avoiding duplicated model controls or a parallel metadata cache. We have not substituted TestOnly extension registration APIs.
6. Platform lifecycle: `DisabledPluginsState.addDisablePluginListener/removeDisablePluginListener`. Public disabled-state queries are available, but we found no public topic for pending disable/re-enable changes. Dynamic unload alone does not cover restart-required changes. Classloading now uses the documented dependency graph and is no longer part of this request.

We inspected all declared extension-point contracts in Air 262.8665.497/263.7031.23 and Assistant 262.10968.223/263.7031.23, not just the migration table. Public Air `AgentThreadLaunchSpecAugmenter` and `AgentThreadLaunchContributor` are consumed by the launch-spec planner; the composer prepared ACP path instead invokes `AgentSessionRuntimeAdapter.prepareLaunch` and `AcpSessionManager.prepare`. We did not establish that those public hooks can supply the composer-local ACP start configuration before preparation. `AcpAgentStartConfigOverrideProvider`, which appears closer, is explicitly Internal in both target artifacts. Is there a supported way to bind that configuration on the prepared path?

We also evaluated public `EditorTextField.getDocument()` as an alternative to `AIInput.document`. The actual composer returned different Document instances (equal text at the observation), so the substitution was reverted rather than assuming read-only/listener semantics are equivalent. Public legacy `ChatMessageViewProvider`/HTML-part extensions and additive toolbar providers likewise did not expose the ACP header/decorator hooks we need. These are scoped findings; we do not assert that all Air/Assistant APIs are private or that no alternatives exist anywhere.

We also disclose existing reflective/private pinned-host adapters for native preferences, authentication, launch and consented recovery. These are not exhaustively represented in the verifier's bytecode-visible count. For example, defaults discovery still accesses Air's private `AcpInitializedClientFactoryKt.acpClientInfo()` to obtain the real native client capabilities/implementation; public class resolution does not make that method public. Is there a supported client-initialization metadata factory for this purpose? We have not moved any reported usage into reflection or suppressed warnings to bypass verification. We would prefer supported APIs for these boundaries as well.

The attached audit inventory can provide every API signature and plugin usage location for both builds. Please advise whether separate YouTrack requests should be opened for Air, AI Assistant and the platform lifecycle topics, and which APIs should be used. If particular current usages can be permitted, please confirm their exact scope and conditions explicitly. We will not assume an exception from the lack of alternatives.
