# Send disabled after reopening a chat — dev.68

Read-only runtime inspection of the primary IDEA found four open AI Multi inputs with `isSendActionEnabled=true`, `isAnyModelAvailable=true`, `isAgentReady=false`, writable/enabled editors, and a native provider readiness result of true. Three retained an acquired session through the final snapshot; the fourth had one in the initial snapshot. Native logs also recorded `Action was disabled in presentation`. No prompt text or provider history was copied by the diagnostic snapshot, and no prompt was sent to a production agent.

The pinned Assistant input combines provider readiness with `AIAChatInputProxyMonolith.isInitialSetupCompleteFlow`. That flow inverts `hasInProgressPrePromptBlocksFlow`, which tracks block event IDs until the first user prompt. AI Multi published an extra IN_PROGRESS authentication block before native restoration replay, then published completion after acquisition. The replayed first prompt could end that native collector before the completion arrived. Merging status IDs in the custom response view could only hide the symptom visually; it could not repair the native input collector.

Removed AI Multi's synthetic preparation/success/failure events and its response-view status merging. Native acquisition, authentication, errors, readiness, Send validation and provider events remain with the host. Profile preference synchronization still uses the native lifecycle and configured ACP settings. Router sources, provider capabilities, load/resume selection, session IDs and Default Profile are unchanged.

The isolated native fixture restores saved Assistant history, focuses the actual chat panel, reads the native Send presentation, invokes the ordinary registered Send action and requires a new session/prompt at the fixture backend. It also covers successful load without optional config options. Reinstating the prior preparation/completion emissions fails this fixture with `isAgentReady=false`, `enabled=false`, `Normal Send disabled` (build/send68/baseline-send-state.txt and baseline-error.txt). Removing them passes with `isAgentReady=true`, `enabled=true` and a prompt on the original fixture session (build/send68/send-state.txt, result.txt and backend-trace.jsonl). The probe uses synthetic profiles and never contacts production providers.

Debugger status reported no sessions, and the available IDE run configurations did not contain a relevant launch/attach configuration. Runtime evidence therefore came from a read-only diagnostic agent and an isolated runIde integration probe, rather than debugger logpoints. The primary IDE was not suspended or restarted, and no primary chat/history was changed.
