# Cross-client native architecture audit — 2026-10-17

Scope: current dev.84 source, Air and AI Assistant adapters, common router/settings policy. This audit records rework requirements; it does not claim that the proposed architecture has been implemented. The [shared contract](native-client-architecture.md) applies to both clients and future IDE clients.

## Existing shared behavior to preserve

`router/profile-settings.js` already owns default application, remembered-preference precedence and filtering for both clients. `ClientPreferences.kt` supplies one storage boundary with client-specific native stores and stable profile/agent storage keys. `router/cps-router.js` and `virtual-sessions.js` own routing, real agent negotiation and committed segment restoration. Missing defaults do not trigger automatic catalog capture. Keep this policy shared rather than implementing another precedence/filter engine in an Air factory.

`profile-settings.js.filterModels` starts with the agent result, preserves unknown result/option fields and nested groups, filters explicit exclusions, and does not synthesize missing models. It retains an accepted current model even if subsequently excluded. Preserve this existing accepted-state behavior while agreeing any change separately. Profile defaults and remembered client values remain independent of agent-owned catalog discovery.

`compat/ProfileChatCreator.kt` already creates a native AI Assistant chat and stages its explicit profile before focusing the chat. This is a useful existing boundary: profile routing before native acquisition, with an unchanged project Default Profile. Reuse its client-independent routing intent; do not copy Assistant chat creation APIs into Air.

## Internal adapters needing verification, not automatic removal

These are specific areas where the implementation is broader than simple launch/profile binding. Source inspection identifies risk and required proof, not a demonstrated regression in every path.

- **Assistant startup:** `ProfileStartupStatus.observe` can call `ensureSessionReady` under its authentication/lifecycle guards and installs a before-prompt hook. `ProfileAgentPreferences.beforePrompt` appends to a private native action list. Determine which parts are required to bind profile settings and which duplicate native startup. Keep synchronization idempotent and prevent extra acquisition/setter calls caused solely by rendering.
- **Assistant native controls:** `ProfileToolbarIsolation` globally masks native toolbar providers, delegates unrelated chats, supplies a chat-scoped presentation identity and polls for an existing session every 100 ms. It preserves native controls but is an invasive host adapter. Verify ordinary agents remain behaviorally unchanged; prefer native scoped/reactive APIs when available, retain account isolation, and avoid multiplying collectors/side effects from both menu and toolbar subscriptions. `ProfileCatalogPresentation.seed` intentionally waits for real metadata in a pending new chat; native cache integration must be investigated before promising an equivalent deferred path in Assistant.
- **Assistant tasks:** `ChatHandoffClient.continueNow` mirrors native task preparation through private mutex/task/state methods; `updateSteeringSupport` mutates native cached fields from target metadata. Minimize this to supported native operations wherever available. A changed agent's real initialization/capabilities must remain authoritative; updating a steering boolean alone is not proof of full native equivalence. Preserve consented continuation, tools, cancellation, completion and restoration tests.
- **Assistant loading:** `ChatSwitchUi` tracks operations by project and may cover the tool window. Keep loading/event blocking scoped to the profile operation where necessary, and verify it cannot unnecessarily block unrelated chats. It must hand control to native task progress once a task starts.
- **Assistant profile attribution:** `ProfileResponseHeaderProvider` is a first-priority split-component provider, and `ProfileHeaderWrapper` paints profile-specific headers over the native view. This is existing profile attribution, not model discovery, but it is custom presentation. Keep it separate from startup/settings changes and verify native message layout, accessibility and unrelated chats; prefer narrower native attribution hooks when available.

The shared protocol contract still requires transparent forwarding, ACP v1 negotiation, exact load/resume choice, unchanged errors/extensions and no old session ID sent to a replacement agent. Native clients may legitimately differ in cache or startup behavior. Do not manufacture uniform behavior by fabricating protocol readiness or capabilities.

## Regression gate and current evidence

Run the same behavioral contract for Air, Assistant and future adapters: direct selection versus the same profile-bound agent without overrides; initial routing to the selected profile; partial/full defaults and accepted user changes; model filtering without catalog replacement; profile/account/cache isolation; native first prompt/tools/cancel/completion; unchanged draft/layout/project default; exact restoration; and consented transfer in an existing conversation. Standard agents and unrelated chats must be included. Air-only verification is insufficient for a shared change.

For this audit, the existing shared suites `router/test-client-preferences.js`, `router/test-concrete-defaults.js` and `router/test-transparent-proxy.js` passed. `tools/VerifyClientPreferences.ps1 -OutputDirectory build/shared-architecture-audit` also passed with both actual native client adapters and controlled ACP backends; it was run without `-AirOnly`. It covers native stores, an Assistant chat with native task/cancel behavior and explicit remembered selection, plus actual Air admission/settings/profile switching. No production accounts or primary IDE chats were used.

The native suite separately reproduces the already documented `startedNewTurn` completion gap with and without the router (`routed-steering-repro.txt` and `direct-steering-repro.txt`, both `nativeTaskStillActive=true`). A passing audit run does not mean this upstream issue is fixed, nor does this existing suite prove that every desired future cold/warm-cache scenario is already covered.

Only architecture/decision documentation was changed for this cross-client review. No production implementation, plugin version, factory registration or deployment changed. The earlier application-wide Air factory proposal remains unapplied after automatic review rejected its blast radius. Select a narrow, reviewable integration mechanism and verify both clients before shipping the rework.
