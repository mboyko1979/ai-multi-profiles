# Native client and profile responsibilities

The shared contract applies to every supported native client.
The same architecture applies to Air, AI Assistant and future IDE clients. Selecting a profile indirectly selects an agent and its profile-specific environment. After that resolution, the client should work with the bound agent as it does after selecting that same agent directly, wherever native integration permits. Explicit profile settings and required profile identity/routing are the intentional differences; a separate client behavior or lifecycle is not a product goal.

| Responsibility | Owner |
| --- | --- |
| Profile CRUD, credentials/environment isolation, project Default Profile, per-chat/composer selection and routing | AI Multi shared profile layer |
| Catalog contents, model IDs, capabilities, protocol behavior, accepted values, notifications and errors | Bound agent, through the native client/transport |
| Configured default selections and model inclusion/exclusion over agent-sourced metadata | AI Multi shared policy layer |
| Composer/chat layout, native model/settings controls, loading, metadata caches, preparation, prompting, tools, cancellation and task completion | Native client |

The two execution-policy layers are profile/agent resolution and explicit default/filter application. Profile administration and existing consented history transfer remain AI Multi features. Profile attribution UI must stay a narrow addition. The agent supplies catalog metadata; the client renders the dropdowns. Profile selection never changes the project's Default Profile.

selecting a launch profile requires no live session, cache lookup, agent discovery or protocol request. Initialize the composer's own selection from the project Default Profile. Subsequent choices belong to that composer. Agent metadata can still be loading while this selection is already complete. Any unavoidable native binding must be scoped to the AI Multi composer and justified separately by the need to carry its launch routing, not by profile choice itself.

## Shared implementation and host adapters

Profile resolution should produce a client-independent launch description: stable profile UUID, bound agent identity, executable/arguments/environment and explicit settings policy. Keep profile identity and launch preparation separate from a live session. Share policy for defaults, remembered-preference precedence, filtering, cache identity/invalidation and consented routing; preserve existing protocol transparency and restoration rules.

Host adapters translate that description into native launch/selection APIs, bind remembered-preference storage, and pass agent-sourced metadata through the shared overlay. They expose only functionality the client actually supports. They must not independently decide precedence, reconstruct the agent's catalog, choose substitute models, replicate a preparation/task runner, or wrap the client's metadata cache. A future client adds native bindings and contract tests, rather than another copy of profile policy. Client-specific remembered preferences remain independent.

Current shared pieces are `router/profile-settings.js`, routing/virtual-session modules and `ClientPreferences.kt`/`NativeClientPreferenceStore`. Keep them shared. `ProfileLaunch.kt` provides shared launch resolution used by both clients and explicit startup staging for AI Assistant. Air binds the selected launch on its own composer instance. Cache/presentation integration is not yet unified: see the [cross-client audit](native-client-audit-2026-10-17.md).

`compat/ProfileAgentUpdates.kt` binds Assistant 262's native terms and pre-prompt registry update checks to the current segment's agent ID. The native services own admission, update eligibility, installation, progress and consent. A successful installation refreshes routes and uses the host's resubmission event, session-init lock, reload invalidation and process-handler stop for this chat. An in-flight snapshot preserves accepted choices until the updated native session validates/restores them; it is cleared on restoration or owner disposal. This pinned adapter is needed because Assistant otherwise checks only AI Multi's local registration, which has no registry distribution. It owns no installer, preparation runner or metadata cache. Changed identities still require router recovery; advanced command overrides remain explicit custom launches.

`air/AirProfileAgentUpdates.kt` records the selected managed agent's actual usage, invokes Air 262's own updater with only that registry candidate, and joins the native per-agent installation coordinator before launch resolution. The scoped composer delegates catalog origin and admission to the bound entry. An explicit in-chat switch checks the native provisioning verdict before modifying the binding. Air's native background updater, policies, attempted-version bookkeeping, installer, progress and consent remain unchanged. Local command overrides do not trigger registry installation or update through this adapter.

`NativeSdkBinding`, Assistant's prepared-session binding and `air/AirProfileBinding` are pinned 262 adapters for replacing accepted initialization/session metadata after an explicit profile handoff. Air retains its actual facade SDK handles, live flows, connection, thread and task owner; only accepted metadata/configuration and that connection's native pool facts are changed. Assistant replaces its SDK handle through the same native holder/init lock used for prepared drafts. The router buffers target notifications until binding is acknowledged and returns the source's real metadata on rollback. These private field/constructor/snapshot dependencies require renewed verification when the host changes; they add no plugin catalog cache or task runner.

## Native startup and catalog overlays

`air/AirLegacyProfilePresentation` supplies only the non-launchable historical `acp.ai-multi` alias. It delegates to the registered native `AcpAgentCatalogContributor`, sharing its lifecycle and caches. Air 262.8665.512 changed Kotlin constructor default masks and introduced a cold `declaredSnapshot()` path; the adapter discovers that zero-argument method reflectively and otherwise uses the pinned 262.8665.497 `snapshot()` API. Native invocation errors are unwrapped and propagated. It never constructs a second catalog contributor or starts a separate runtime to obtain the alias.

The .512 launch adapter retains the complete native preparation request in its lease key rather than reading the removed `destination` field. Its start-config delegate appends only `--initial-profile` and preserves that argument after native environment overlays, without the removed `withAcpArgs` method. Defaults discovery passes the project's native Eel descriptor to the newer client-info factory. Air preference writes use native default-copy semantics to preserve trailing session fields such as .512's `fastMode`; no new setting or default is invented by AI Multi.

The scoped composer runtime and prepared-session backend use the host's zero-argument constructors to obtain native defaults, then bind the runtime primary constructor by its instance-field types. Only the launch-entry/adapter resolver is replaced. This avoids the removed .497 Kotlin default-constructor descriptors on .512 and retains the newer host's cloud, ownership and prompt-support dependencies. The field order/types remain a pinned host dependency and must fail explicitly if they no longer match. No application-wide adapter is replaced.

Composer launch seeds bind the runtime data-class copy by its actual field types, preserving untouched native fields (including .512's `fastMode` and draft prompt). This avoids a compiled call to the removed .497 `copy` signature. Account attribution reads only the current native lane's agent identity flow; the generic AI-source caption can describe an unrelated IDE account. The scoped caption overlay removes native text segments that would override its agent/profile caption, and uses `Account unknown` when neither agent nor profile supplies identity. Native account actions and lifecycle remain delegated.

For an already prepared, unsent draft, retain the native chat/composer and the real prepared sessions across profile choices. Returning to a profile reuses its native handle and original session ID. Release unused preparations after the first message is accepted, or when the draft is abandoned. This adds no need to recreate an empty chat; it adds no metadata cache or requirement to acquire a session before recording a local choice. See [verification limits](verification.md).

After Air accepts the first prepared prompt, persist AI Multi's transport agent/launch target in its native append-only session log. The composer's bound-agent route still supplies native catalog presentation and preparation. Its scoped launch resolver does not survive runtime release, so persisting that provider route alongside an `aiaps-chat-*` ID incorrectly sends the virtual ID directly to the provider on restore. `AirChatRoutingRepair` changes only these routing fields after verifying the local conversation ID and working directory; session ID, profile, history and unknown binding fields remain intact. The native identity registry must also associate the same local chat and virtual ID with AI Multi?s namespace; retaining the provider namespace leaves Air?s surface/source routing inconsistent. Existing affected chats are eligible only after ID/cwd ownership checks.

Air's new-session tab icon normally follows the bound agent's launch profile. The pinned Air adapter associates the composer with its open virtual file using Air's tab key and marks that file while the composer belongs to AI Multi; it refreshes the native file presentation when ownership changes. Committed sessions continue to use their routed session ID. Native activity and access badges remain in use.

An opened, disconnected AI Multi chat observes Air?s native restoration result once. When its unbound generic entry cannot restore, `AirChatRoutingRepair` binds `--restore-session` on that failed runtime?s entry and reuses `AirProfileBridge.connect`, the existing pinned recovery adapter. Air?s own executor, admission, owner, protocol session, task and completion machinery remain responsible for connection/restoration. It adds no preparation/task state machine, retry loop, live-session requirement for profile selection, or global resolver replacement. The existing pinned recovery helper waits for its admitted native connection. This narrow executor adapter is unavoidable on the pinned host: `AcpSessionLaunchResolver` otherwise re-resolves the generic registration, while its start-config override API receives no conversation identity. The 497 six-field connection request and 521 target/purpose request are bound explicitly. Closed surfaces, disabled/missing agents, connected owners and a previously attempted scoped restore are not automatically retried. An explicit **Reconnect chat** action remains available on failure.

The router bootstrap resolves the last committed segment before initialization, retains its launch directory, and forwards the real agent?s initialization and the client?s selected load/resume method. Changed-agent recovery still uses the existing consent path. A restore-bound connection rejects replacement session creation. Repair never transfers history, changes an active connection, synthesizes readiness or changes the project Default Profile. The reflective log adapter supports the pinned 497 model package and 521 shared-event package; identity association also preserves the 497 aliases parameter.

For Air New Session or AI Assistant New Chat, resolve the selected profile and its bound agent before the native client acquires the initial agent session where its APIs permit. Supply profile-scoped native launch metadata and seed selections. The common filter removes only configured exclusions from the real catalog and preserves unknown fields/groups; it never fills the list from a hand-maintained replacement. Keep newly reported agent models available unless an explicit policy excludes them. Explicit defaults are selections, not a source of models or evidence that a session is ready.

Let each client render its native controls and decide between supported cached/deferred/live preparation paths. Do not add an AI Multi requirement for synchronous session creation merely to show an accepted cached catalog. Air may still prepare in the background or start after a native interaction despite a cache hit; AI Assistant may have a different native policy. Do not force both clients to copy Air's lifecycle or promise that cache hits never start a session. An unavailable cached/configured value must be resolved against the real agent rather than invented. A display cache is not a live ACP session and must never authorize sending an old agent's session ID to another agent.

Do not build replacement windows, parallel model/settings dropdowns, a parallel UI cache or a second session-preparation state machine. Avoid manually calling connection executors, rehydrating ownership, polling readiness or opening another view solely to select a new launch profile. A narrow host adapter may bind profile identity, launch arguments, native preference seeds and agent-catalog overlays; it must delegate rendering and lifecycle to the client, preserve unknown native actions/fields and document its pinned API dependencies. A global factory/provider replacement is not justified merely because the shared architecture is approved; its scope and unrelated-client behavior require concrete review and verification.

Do not add a plugin metadata cache and do not wrap or suffix the client's cache key with a profile UUID. Catalog isolation is the bound agent's native cache: a Grok profile uses Grok's Air cache, a Codex profile uses Codex's. Two profiles of the same bound agent share that agent's cache. Keep plugin/ACP registration IDs stable, do not add duplicate user-visible agents to obtain separate cache keys, and never mutate the project's Default Profile during chat selection. Explicit defaults precede that client's profile/agent-scoped remembered preferences; absent selections preserve the real agent's values.

Existing conversations retain their committed profile/agent segment and accepted settings. A deliberate switch in a conversation with history remains a consented routing/history operation, distinct from choosing a New Session launch profile. Preserve native session admission and completion; do not synthesize ACP capabilities or success.

## Verification across clients

Every change to shared routing/default/filter code must pass both clients' contract tests. An Air-specific lifecycle/cache change must also pass AI Assistant regression verification, and conversely. Cover direct agent selection versus the same agent through a profile with no explicit overrides, cold/warm cache, partial/complete defaults, model filters and new agent models, independent account catalogs/preferences, unchanged draft/layout/default profile, first native prompt, tools, cancellation, completion, restoration and consented history transfer. Compare observable behavior and preserve unknown protocol fields/errors; stable routing IDs and authorized profile overlays are expected differences.

Use native verification for both clients in an isolated IDE; do not infer AI Assistant safety from an Air-only run. Keep standard agents and unrelated chats in the regression scope. Timing claims require measurements; existence of a cache alone does not prove which path a particular production session used.
